## 使用入口与本版边界

- **常规周报简版**：任务卡 → 训练问题准入 → 冻结训练底稿 → 训练统计 → 证据核对 → 用户讨论。没有相关问题时，不强行展开饮食、身体或模板模块。
- **专题联合版**：在简版基础上，选择第 5 节的问题模板，只加入该问题需要的数据域和比较窗口。
- **工具尚未就绪时**：按第 8 节记录差异，独立重算受影响指标并保留查询；不得把本文件的规范定义当作工具已经实现的行为。
- **历史状态另存**：初稿时的数据数量和一次性动作移至附录 A；末尾上一轮复核意见原文保留，不随正文修订覆盖。该意见由 AI 提出、用户要求归档，不表述为用户撰写的复核结论。
- v0.4 文档修订轮只完善流程文档：当时没有修改导出代码、离线入库、创建分析产物包或生成个人结论。后续工具实施状态见第 8.1 节；历史复核记录保持原文。
- 修订依据：[v0.2 复核结果](analysis-workflow-review-v0.2.md) 的四项定义和两项补充在 v0.3 中处理，历史对照见第 8.4 节；本轮按对话中独立核验及用户确认的方案修订四处边界，见第 8.5 节。既有复核文件保持原样，文档修订不代表工具验收通过或形成个人训练判断。

## 1. 分析目标与基本约束

每次分析依次回答：

1. **数据是否足够可信？** 查询范围、同步覆盖、入库情况、缺失字段和统计口径是否明确。
2. **实际做了什么？** 训练完成情况、已记录饮食、每日目标和身体测量。
3. **与什么相比？** 同类训练、历史阶段、当时有效的计划；不能随意选择参照。
4. **哪些只是可能原因？** 将事实、计算结果、假设和已确认决策分开。
5. **下一步如何验证？** 优先提出可复核的问题或观察任务，再与用户讨论是否调整。

基本约束：

- **本地优先**：默认不联网；同步、刷新或写回必须有用户明确要求。
- **数字由 Python / SQL 计算，模型负责解释**；模型不得凭记忆补数或心算大批明细。
- 不修改 `data/raw/`，不把密钥、鉴权头或 `.env` 内容放进分析材料。
- 缺失不等于零，未记录不等于未发生，相关性不等于因果。
- 当前训练目标、记录习惯和主观感受未知时，标明未知，不自行假定正在减脂、增肌或执行某种周期。
- 身体数据只做训练相关的描述与谨慎讨论，不做医疗诊断。

## 2. 当前可用数据与入口

### 2.1 数据类型

| 数据 | 本地入口 | 可以回答的问题 | 主要边界 |
|---|---|---|---|
| 训练记录 | SQLite 的 `training_session`、`training_set` | 次数、训练日、动作、完成组、重量、次数、容量、RPE | 训练次数与训练天数不同；未完成组不计完成容量 |
| 有氧与心率 | `cardio_record`、`heart_rate_summary`；必要时核对对应 Raw | 有氧记录、时长、距离、设备报告的热量与心率 | 指标单位与来源必须核对；无心率不能推断心率区间 |
| 饮食 | `food_day`、`food_record`；旧记录先从 Raw 离线导入 | 已记录摄入、餐次、营养组成、每日 `limits` 及偏差 | 记录完整性需用户确认；`limits` 不等于 TDEE |
| 身体 | `body_record` | 按日期、类型、单位查看体重等变化 | 可用类型按本次盘点；稀疏测量不能当成连续趋势 |
| Agent 个人模板 | `agent_template`、`access_state`；增量 Raw | 当前模板、版本、目标动作/组次、递增规则 | 只覆盖 Agent 专属文件夹；当前模板不证明过去的计划或实际排期 |
| 官方计划与讨论记录 | `data/plans/`、`plans/current.md`、`reports/weekly/`、`notes/` | 计划背景、历史判断、已确认的调整 | 需区分官方计划、个人模板与已经生效的个人决策 |

模板当前返回的是原生 `movement` 与 `rules` 结构，不应假设一定有公开写入格式的 `movements`。分析前检查字段结构、可读动作标签、组结构、单位与规则；无法解释的字段保留原值并列为待确认项。不能把 `currentWeight`、`doneNumber`、`doneVolume` 等模板状态直接当作历史训练事实。

### 2.2 按问题准入与降级，不作整次分析的全有或全无判断

先分别记录两种完整性：

- **同步完整性**：在指定查询条件与采集时点下，所需日期已成功获取、分页已完成、数据已入库且证据可回查。模板还须核对游标、内容模式、folder 及删除事件。
- **记录完整性**：用户是否完整记录了真实训练/饮食，以及确认适用的具体日期与范围。取值为“用户确认完整／用户确认不完整／未知”，不从接口成功或食物条数推导。

同步完整不能证明记录完整；历史成功响应也不证明来源此后没有修改。记录各域实际采集截止时间，不用本地 `updated_at` 冒充 API 拉取时间。缺体重不阻断训练统计，缺模板历史不阻断实际训练描述。

| 问题 | 完整回答的必要条件 | 不足时的输出或停止范围 |
|---|---|---|
| 已记录训练次数、完成记录段 | 所选记录已正确入库，明确 SQL 展开行和完成标签的口径 | 列已记录数量及未知覆盖，不称为完整实际频率或逻辑正式组数 |
| 逻辑正式组数 | 原始结构、完成/热身语义和计数层级已核实 | 结构未恢复时只列记录段；部分恢复只描述已核实组数，不当作总正式组数 |
| 完整训练频率或周总量变化 | 所选窗口同步覆盖可核实，记录完整性与可比口径明确 | 只描述已记录数量；部分周不得直接比较完整周总量 |
| 同动作表现变化 | 动作、单位、器械/执行条件可比，存在预先定义的基线 | 分列原始表现，不判进步或退步 |
| 已记录饮食目标偏差 | 日期对应的有效摄入和有效目标；比率另需目标大于0 | 缺目标仅展示摄入；有效零目标只算差值；零语义未知不算；缺摄入不以零代替 |
| 实际饮食目标执行 | 上述条件，加对应日期记录完整性确认、已约定判定标准 | 仅称“已记录摄入偏差”，不作实际达标判断 |
| 历史计划执行比例 | 当时有效版本、适用排期、实际训练映射及分子分母已确认 | 只描述当前模板和历史实际记录，不算历史执行比例 |
| 饮食与训练联合解释 | 可配对日期、可比训练、事先选择的饮食窗口与必要背景 | 降级为带缺失标记的时间线，不作营养导致表现变化的解释 |
| 体重趋势 / 能量收支估计 | 测量频率和条件满足预设规则；能量估计另需较完整摄入与充分时间窗 | 稀疏时仅列实测点与明确日期差值，不反推精确 TDEE |

每个问题输出 `eligible`（准入）、`descriptive_only`（仅描述）或 `blocked`（关键口径/数据无效），并写明原因与补充条件。没有记录不会自动成为 `blocked`；不能可信计算的那个指标才停止，其余问题照常执行。

### 2.3 指标字典与统一计算约定

本版定义分析口径版本 **`analysis-metrics-v2.1`**，与数据库 schema 版本分别管理。v2 相比 v1 拆开记录段与逻辑组、补充单位/负重语义验证、容量状态及零目标条件；v2.1 在此基础上细化容量无效字段、无 `sets` 原生有氧及零值与 `null` 混合汇总的判定边界。迁移时须按 v2.1 重新核验相关来源并重算容量数值、状态及覆盖，不能只改版本标签或直接拼接旧趋势；旧运行及定义保留，计数层级与饮食目标定义沿用 v2。下表是规范定义，尚不表示导出脚本已经全部实现。

通用规则：

- 日期窗口含首尾；先限定任务日期，再应用各指标自己的筛选。不将筛除记录从底稿中删除，保留数量、原因和定位键。
- `null` 表示未知/不适用，数值 0 表示有证据支持的零；分母为 0 或目标无效时，比例输出 `null` 并给原因，不输出 0% 或无穷大。
- 机器底稿保留来源精度；展示时按登记的精度舍入，不能用已舍入的数重新累计或判断临界值。
- 以下每个指标的落盘实例均需绑定：ID、口径版本、来源字段、日期、筛选、单位、样本数、分子/分母（适用时）、缺失/排除规则、查询及证据编号。

| 指标 ID | 来源与筛选 | 公式、单位或分母 | 缺失与适用范围 |
|---|---|---|---|
| `training.sessions` / `training.days` | `training_session`，任务日期内 | 行数 / 不同 `datestr` 数；次 / 天 | 列覆盖状态；一天两次是两次、一天，不按标题猜运动类型 |
| `training.completed_segments` | 当前标准化展开行中 `done=1 AND is_warmup=0`；关联任务日期 | 完成记录段数；计数单位明确为 `normalized_row` | 这是数据库展开记录数量，不是逻辑正式组；无法恢复原始结构时只报告该数，注明可能遗漏完成标志/热身继承，不能直接用于模板执行率 |
| `training.work_sets` | 按第 2.3.2 节从 Raw 恢复、类型适用且完整完成的逻辑正式组 | 按已冻结结构规则计组；单位 `logical_set` | 未恢复结构时为 `null`；结构只部分确认时仅附“已核实组数”，不冒充该区间总正式组数 |
| `training.volume` | 经语义/结构验证的独立完成非热身抗阻段，重量/次数为有限正数、负重为可计外部重量 | 每个独立实际段只算一次 `Σ(weight_kg × reps)`；kg·次 | 不计父级汇总、重复子段或辅助重量；缺失/无效字段及无段结构的不适用记录均参与状态判定，零值、部分合计与各类 `null` 按第 2.3.3 节分开 |
| `training.volume_coverage` | 可计算独立段数 / 所选范围已核实完整的完成非热身候选段数 | 按段计，不按逻辑组计 | 结构未恢复完整、分母不可知或为0时比率 `null`，另列已核实可算段数和未解析结构；无段结构的有氧不虚造段数，另列记录及不适用/排除原因；覆盖率不能代替容量状态 |
| `training.rpe_mean` / `training.rpe_coverage` | 类型适用、独立完成非热身段的有效独立评分；按当前训记约束核对6—10、半档步进 | 段级 RPE 均值；独立有效评分段数 / 对应候选段数 | 显式标“段级”；父组共享评分不复制给各子段，单独保留；结构/分母未知则不算覆盖率，异常不裁剪 |
| `training.high_rpe_share` | 与段级 RPE 均值相同的独立样本 | RPE≥9 的独立评分段数 / 有效独立评分段数 | 不是占全部训练行或逻辑组的比例，也不是疲劳诊断 |
| `training.max_weight` | 本期与历史均限定同动作、独立完成非热身段、单位及负重语义可比 | 正外部重量最大值；kg | 辅助重量不混入，纯自重/计时不套用；列历史边界及段类型，不把递减段最大值当成整体 PR |
| `training.session_duration` | 每条 session 的有效 `duration_s`，独立于组表汇总 | 秒，可换算展示 | 缺失/负时长排除并计数；重叠训练时段的简单相加须标“记录时长之和”，不能冒充不重叠活动时间 |
| `food.recorded_day_mean` | `food_day` 中该营养素/热量数值有效的记录日 | 有效日摄入合计 / 有效记录日数；kcal/日或g/日 | 各指标分别列有效记录天数及区间天数，不用所有日历日或其他营养素的样本数作分母 |
| `food.target_delta` | 同日、同一指标的有效摄入与明确有效目标；目标可为已证实的零 | 已记录摄入−目标；g 或 kcal | 零若表示未设置或语义未知则按缺目标；保存目标有效性依据，不对差值取绝对值 |
| `food.target_delta_ratio` | 同上，另要求目标严格大于 0 | 差值/目标；无量纲 | 有效零目标也不算比率；其有效日期集合可能与差值不同，分别输出分母与排除原因 |
| `food.target_attainment` | 已确认记录完整的日，目标与用户认可的容差均有效 | 容差内日数 / 符合条件的配对日数 | 未约定容差时不计算；周合计偏差不能替代逐日执行情况 |
| `body.measurement_delta` | `body_record` 同类型、同单位、明确的两次实测 | 后值−前值，同时输出两日期 | 不跨长间隔插值；未知测量条件限制解释，不推导体脂/肌肉变化 |
| `body.window_mean` | 预先声明窗口内真实、条件可比的测量 | 有效实测均值，附测量数/天数 | 最小频率、最大间隔在任务卡约定；不满足则仅列点位，不能把单点均值包装为平滑趋势 |
| `template.execution_ratio` | 已确认适用版本/排期且可对应的模板与实际记录 | 已完成且可匹配的目标组数 / 当期应完成的目标组数 | 额外组另列，不让分子靠多做变成超过100%的“依从性”；动作替换/未匹配组单列；条件不明不算 |

比率聚合必须标明采用“逐日比率均值”还是“合计分子/合计分母”，两者不能混用。饮食摘要默认输出**有效配对日的平均差值（单位随指标：g 或 kcal）**和配对样本数；这是摄入减目标的有符号差值，不是绝对值均值。比率另用目标大于 0 的日期集合并公开其样本数；需要并排比较两种统计时，另给共同日期子集结果，不能假定两个分母相同。

模板目标组匹配须使用唯一目标定位键，每个应完成目标至多计入一次分子；多做的组、替换动作和匹配不明的记录分别展示，不靠截断一个超过100%的比率来掩盖重复匹配。

有氧距离、设备热量、心率区间等专题指标，须先补齐各自来源单位、设备口径与指标定义；未登记前只展示原始记录，不跨不同运动/设备混加成统一表现分数。

#### 2.3.1 先恢复动作、单位与负重语义，再计算

**已核实的工具限制：** `training_set` 没有完整保存原始单位、计时/自重标志及负重角色；`normalize.py::_weight_kg()` 只特殊转换 lb/lbs，未知单位仍可能原值写入 `weight_kg`，缺单位也会默认 kg。因此，SQL 列名或正数值不等于单位和语义已经验证；也不能仅凭动作名称或数值推断。

所需字段不足时，只读取已定位的对应 Raw，在运行包中生成可追溯的派生事实，不修改 Raw 或凭空补写活动库。每条至少保留：

- 来源快照 SHA-256、训练日期/来源训练 ID、原始动作位置、组/轮/子项/子段的 JSON 定位路径；数据库行 ID 只作为冻结库内的辅助关联。
- 原始重量、原始单位、次数、计时/有氧/自重标志及其来源字段，解析后的数值、单位转换依据与规则版本。
- `movement_type`（抗阻/计时/有氧/未知）、`load_role`（外部负重/纯自重/辅助重量/未知）、单侧/双侧记录语义和映射证据。
- 每个字段的已确认/未知状态、判断依据、结构父子键和适用/排除原因。不能把规则推断与 API 明确字段标成同一种来源。

| 原始情况 | 分析处理与验收规则 |
|---|---|
| 明确 kg，且语义为可计外部负重 | 验证完整数值及单位后使用；必须能回查到明确单位证据，不只读现有 `weight_kg` 列 |
| 明确 lb/lbs，语义同上 | 按 `1 lb = 0.45359237 kg` 转换，保留原值与转换规则；已有转换值不得再次转换 |
| 单位缺失、未知或为器械档位 | 不沿用标准化时默认 kg 的行为；没有可核实的单位约定则排除吨位/外部最大重量，记录原因 |
| 计时/有氧记录 | 计时数字不作为重量或次数；按已验证的时长、距离等专题口径处理 |
| 纯自重 / 明确额外负重的自重动作 | 纯自重不补体重计吨位；明确额外负重时仅计该部分且标“外部负重口径”，不与含自身体重的估算混合 |
| 辅助重量、弹力带等级等 | 不将正数直接当成克服的外部负重，不擅自以体重减辅助量计算有效负荷；可在同器械、同单位、同语义下单列描述 |
| 左右侧或单双哑铃口径不明 | 保留来源口径并限制比较，不自行乘2、合并或推定为总重；矛盾字段标为冲突 |

未知语义只阻断依赖它的指标，训练记录数量仍可描述。对外声称“可比”之前，单位与负重角色、动作类型和结构解释必须都能从冻结的内容中恢复。

#### 2.3.2 记录段、逻辑正式组、模板目标组分别计数

现有标准化会展开超级组子动作和递减子段，递减子段还会复用父组的 `set_index`；所以 `session_id + movement + set_index` 不是可靠的唯一实际段键，SQL 一行也不必然等于一个训练目标组。

| 结构 | 记录段与逻辑组的约定 | 完成与模板匹配条件 |
|---|---|---|
| 普通单组 | 一个独立实际段对应一个逻辑组；结构已核实时可一对一 | 需有效完成标志和非热身状态；不能因填写了重量/次数就当完成 |
| 递减组 | 每个实际重量段是独立段；完整递减链按一个逻辑组计。父对象若仅为汇总容器则不是实际段，不能再加一次容量 | 所有应完成的必要段都完成，且没有来源标志冲突时才算完整目标组；只完成部分则标部分，不按多个正式组或完整组计 |
| 超级组 | 每轮的各子动作独立计段；逻辑正式组按“轮次×子动作目标组”区分，并另列完整轮数，不能把轮数与子动作组数相加 | 子动作目标分别判断；只有所有必要子目标完成才称整轮完成。轮级模板目标与子动作级目标必须选定其中一个匹配层级 |
| 超级组内另含递减等复合结构 | 只有解释器明确支持并能恢复完整层级时，才按叶段/逻辑组分别处理 | 初版无法完整恢复时保留记录段计数与 Raw 证据，不估逻辑正式组或模板完成比例 |

补充约定：

- 先建立稳定的实际段键和逻辑父组键：来源快照及原始 JSON 路径作为定位依据，并保留普通组/轮次/子动作/递减段层级。模板目标键还须包含模板 ID、适用版本/revision、已确认排期实例和目标结构路径。
- 父组、轮次、子段的完成标志分别保留。缺子段标志时不盲目继承父组 `done`；只有来源语义明确覆盖所有子项、且继承规则已登记并验收时才允许派生，标明其依据。标志冲突单列，不能自动选最有利的值。
- 组状态区分完整完成、部分完成、明确未完成、未知及冲突。`training.work_sets` 统计完整完成的逻辑组，部分组单列；结构不完整时不输出冒充总数的组数或覆盖率。
- 热身属性按已验证的结构传播，不能因递减子段被标为 `drop` 就失去原父组的热身性质。无法确认时排除相关正式组/容量/RPE并说明。
- 容量只汇总可验证的独立实际段，不能同时累计父级汇总与子段；整组未完整完成不妨碍描述其中已明确完成段的可计算容量，但必须与“完整正式组数”分开。
- RPE 先区分评分层级。父组共享评分不复制成多条段级样本；如需组级 RPE，另登记指标及分母，不与段级结果混合。
- 模板完成数的分子和分母必须位于同一结构层级，并包含该目标预定的必要子项；不能拿完成记录行数除以模板组数，不能将部分完成按任意比例折算成完整组。

**初版降级：** 若工具只会数现有展开行，就仅输出 `training.completed_segments`（完成记录段数，单位 `normalized_row`）。`training.work_sets` 与 `template.execution_ratio` 保持 `null`/不可计算，不把该段数重命名为正式组数。旧 v1 的 SQL 行数指标只能以“旧口径”并列说明，不能接入当前 v2.1 沿用的 v2 逻辑组趋势。

#### 2.3.3 容量必须同时输出数值和状态

`training.volume` 的机器结果必须含 `value`、`unit`、`status`、来源覆盖、可算段数/候选段数（可知时）、排除/不适用原因。`status` 与数值共同传递，不能在日级连接或 CSV 导出时丢掉原因而统一补0。

判定范围须覆盖所选训练的动作、`training_set`、`cardio_record` 及必要 Raw，不能只检查组表。原生有氧没有组行，不等于没有完成训练；类型已明确不适用外部吨位时，可判 `not_applicable`，完成状态未知另行保留，不自动使容量变为 `unverified_semantics`。只有可能影响容量的完成/热身或结构语义未知，才据此判语义未证实。没有段结构的有氧记录不虚造为一个段；不能完整确定候选段分母时，`training.volume_coverage` 为 `null`，另列这些记录及原因。

本版可算段仍要求重量和次数为有限正数，不新增零重量或零次数段的可算例外。对已确认应适用的完成段，缺字段与无效字段分别记录；次数≤0、负重量、非有限数或不符合已登记解析规则的值属于无效计算字段，不得乘算或当成未完成。重量0若已证实表示无可计外部负重，按不适用处理；零的负重含义未知则按语义未证实处理。有效容量0只来自下表两类已验证的区间零值情况，不从字段0、空组表或空查询推导。

| 已核实情况 | `value` | `status` 与说明 |
|---|---|---|
| 查询范围已完整同步入库，且有效响应明确无训练 | `0` | `no_training`；表示截至该采集时点的已记录容量为0，不证明没有其他活动；记录完整性另行标记 |
| 有训练，所选范围覆盖完整，且完整核实所选来源的相关记录均明确未完成或为热身，没有除此之外的不适用或待核实记录 | `0` | `no_completed_work`；须验证全部相关来源，不能仅凭没有组行成立 |
| 除已证实未完成/热身的记录外，其余记录非空且全部明确不适用外部吨位，如纯自重、计时、有氧或已证实无可计外部负重 | `null` | `not_applicable`；包括没有组行的原生有氧，不证明没有训练量或已经完成训练 |
| 存在已确认应适用的完成候选段，但这些段均因缺失或无效计算字段而不可算 | `null` | `insufficient_data`；分别列缺失、无效字段及数量，不将异常裁剪、补零或取绝对值 |
| 单位、负重角色、组结构或影响容量的完成/热身语义无法核实，无法确定任何可算独立段 | `null` | `unverified_semantics`；与明确不适用分开 |
| 已有可算段，但除已证实未完成/热身的记录外，其余存在不适用记录、缺失/无效字段、相关语义未证实，或只能证实部分日期/来源覆盖 | 可算部分合计 | `partial`；不适用记录包括无段结构的有氧，仅称可计算部分，附覆盖率/未知分母与全部原因，不当作完整区间总量 |
| 所选范围覆盖完整，存在候选段且所有候选段适用并可算；除已证实未完成/热身的记录外，不存在其他不适用记录（包括无段结构的有氧）、缺失/无效字段或影响容量的待核实事项 | 全部候选段合计 | `complete`；候选口径固定、覆盖率可核对；不能只检查有组行的部分，不表示吨位等于所有运动的训练刺激 |
| 覆盖未知/未入库且没有足够可算证据 | `null` | `coverage_unknown`；不能以库中没有行输出无训练或容量0 |

先验证覆盖证据、结构与语义，再按上述情况判定。所选范围完整满足零值条件时，才输出 `no_training` 或 `no_completed_work`。存在可算段时，满足表中完整条件则为 `complete`，否则为 `partial` 并保留全部原因；明确未完成/热身记录本身不触发 `partial`。没有可算段且不满足零值条件时，按覆盖未知→影响容量的语义未证实→适用字段缺失或无效→明确不适用的顺序确定主状态，其余原因作为辅助原因保留。空的 SQL 结果本身不能证明 `no_training`。

分组/跨日汇总沿用相同原则：只有整个窗口均属于表中已验证的零值情况（`no_training` 或 `no_completed_work`）时，才可汇总为容量0；已知数值与缺失/不适用日期并存时，分别报告已知可算部分与状态分布，不用 `SUM` 忽略空值后将其称为完整总量。

汇总须保留候选段、无段结构的不适用记录、覆盖信息及原因计数后重新判定，不能只累加日级数值或只按状态标签排序：除已证实未完成/热身的记录外，可算的正外部负重段与不适用、无效或未知记录并存为 `partial`；只有已知零和无可算段的日期并存时，零不会把其余日期变为可算，仍按覆盖、语义、字段不足或不适用判读。仅有明确零值日与满足表中 `complete` 全部条件的日时，可得到完整合计。整个窗口均为已验证零值时，全无训练为 `no_training`，否则为 `no_completed_work`。不得因先按日还是直接按周计算而得到不同的容量数值/状态。

#### 2.3.4 饮食目标零值与配对集合

逐指标、逐日期登记目标有效性：有效正目标、已证实有效零目标、未设置、语义未知或无效。确认依据可来自明确接口语义或用户对具体日期/指标的确认，并随本次背景快照保存；不能只凭 `limits` 中出现数字0判定是有效零目标。

- 摄入与目标均有效时计算**有符号差值**，包括有效零目标；例如合成测试中的摄入100 kcal、有效目标0 kcal，差值为100 kcal。
- 比率另要求目标大于0；上述有效零目标的比率为 `null`，不能写0%或无穷大。
- 若0表示未设置、是默认占位或语义未证实，则差值和比率均为 `null`，分别登记 `target_unset` / `target_zero_unknown` 等原因；负数或非有限数属于无效数据。
- 差值均值以有效差值日为分母，比率均值以有效正目标日为分母，分别输出日期集合与样本数。平均差值使用原单位 g 或 kcal，不能把正负相抵后的净偏差当作每日都贴近目标。
- 若用户约定的达标容差仅为相对容差，零目标日不具备判定条件；只有事先约定了适用的绝对容差时，才可把有效零目标纳入达标率分母。仍不得把未确认完整的摄入当作实际执行结果。

### 2.4 先登记比较窗口，再看比较结果

- **展示窗口**：周报仍按 ISO 周；事实表可以展示部分周，但标明截至日期和各域覆盖。
- **表现窗口**：同动作优先选相邻可比训练，或用户已确认的训练周期；分化训练跨周错位不自动等于漏练、减量或刺激下降。
- **体重窗口**：由真实测量频率、间隔和条件决定，不因周报需要而强行每周给趋势。
- **联合观察窗口**：同日、此前若干天或阶段区间只能按任务问题事先约定，不默认固定时滞，也不遍历窗口后仅保留“最显著”的结果。
- 在任务卡中冻结比较对象、选择理由、纳入/排除条件和最低样本要求。没有依据设数值阈值时写“待约定，仅描述”，不为通过准入临时设门槛。
- 查看结果后确需变更基线，应新建修订号，保留原方案与变更理由；按新旧两套口径区分结果，避免事后挑选日期。

## 3. 标准执行流程

流程为：**确定问题 → 检查覆盖与口径 → 生成事实底稿 → 单域分析 → 联合核对 → 模型解释 → 复核 → 用户确认后归档**。

### 步骤 0：建立本次分析任务卡

先记录：

| 项目 | 必须说明的内容 |
|---|---|
| 问题 | 本次要回答什么，例如训练执行、动作进步、饮食目标执行；不是泛泛地“分析所有数据” |
| 目标 | 用户已确认的目标及来源；没有确认则填“未知”，先做描述性分析 |
| 日期 | 明确开始/结束日期、数据提取时间，以及每个数据域的截止日期 |
| 比较基线 | 上一完整周、前 4 周或相邻同类训练；说明为什么可以比较 |
| 准入与窗口 | 每个问题的必要数据域、最低可比样本/覆盖要求、同步与记录完整性分别是什么；采用简版还是专题版 |
| 口径 | `analysis-metrics-v2.1`、选用的指标 ID、段/组/轮计数单位、单位/负重语义、分母、动作映射与指标定义内容、模板历史映射依据 |
| 背景 | 本次读到的周报、计划、观察和已确认决策；占位或缺失的文件应标记 |
| 交付物 | 事实底稿、待讨论问题、拟议建议分别是什么；本轮是否只展示、不写入 |

周报采用 ISO 周，周一至周日。“最近一周”为包含今天的周；尚未结束时写明截止日，不将部分周与完整周直接作总量优劣比较。频率计算须给出实际覆盖天数。

### 步骤 1：本地覆盖与质量审查

1. 查询每类表的记录数、日期边界、关键字段缺失情况。
2. 同时核对 `access_cache` 的查询条件、对应 Raw 和模板游标，而不只看数据库里有没有行。
3. 分清下列状态：
   - 已同步且有记录。
   - 已同步且没有记录。
   - 有 Raw 但尚未入库。
   - 未同步、覆盖不明或记录可能尚未更新。
4. 训练日的空 `trains: []` 可标为“休息（已同步，无训练记录）”；没有本地覆盖证据的日期不能直接标休息。该状态也不证明当天没有其他身体活动。
5. 饮食缺记录不能按摄入 0 处理；空饮水记录不能解释为没有喝水。
6. 检查重复、异常时间、重量/次数单位、空值与数值零。不能按食物 `record_id` 跨日期去重。
7. 记录数据限制：RPE、训练备注、主观疲劳、睡眠、疼痛、体脂、测量条件等是否真正存在。

若某域有 Raw 而尚未入库，只在本次问题需要该域时执行对应的离线导入并核对数量、目标与汇总；不把重新拉取远程数据当作默认修复方式。一次性数量以运行时盘点为准，附录 A 不充当验收常量。

按第 2.2 节给**每个问题**记录准入状态。阻断项输出质量清单和解除条件，描述性项带限制交付，其余问题继续；不因某个可选域缺数据而中止所有分析。

### 步骤 2：生成并核对事实底稿

1. 按项目约定，先运行 `scripts/export.py --week YYYY-Www` 生成训练事实底稿，先不带 `--write`。
2. 阅读目标周及近期周报、`notes/observations.md`、`notes/decisions.md`、`plans/current.md`；必要时再看官方计划。
3. 另用 SQL / Python 计算饮食、身体、模板对照指标；**当前 `export.py` 只导出训练周报，不会自动完成四域联合分析**。
4. 每项数字记录来源表、筛选条件、公式、单位、分母和样本数。
5. 抽样回查：对每个已启用的数据域至少核对一个适用样本；训练查训练日，饮食目标分析查有目标的记录日，模板对照查一组映射，身体查实际测量。纯训练简版不强制检查饮食；不存在适用样本时记录原因并按准入表降级，不为凑样本扩大任务。
6. 发现导出值与本流程口径不一致时，记录差异并单独重算，不静默改写旧报告或把导出结果视为绝对正确。Raw 派生的新口径结果先作为独立核验底稿展示，并按第 4 节约定保存；在满足“数字来自本地库、正式事实章节由 `scripts/export.py` 生成”的链路完成并验收前，不直接替换正式周报第一至五节、第七节，也不将已知有误的导出值作为核验通过的事实发布。此处不预定派生事实的最终库表结构。
7. 按第 4 节冻结来源、计算定义和机器事实产物；主分析与复核都从同一个 `run_id` 读取，不在两轮之间悄悄重查变化后的数据库。

现有导出草稿只有与冻结快照重算结果核验一致后才能纳入本次事实包；两者采集时点有变化时，以新运行 ID 重新提取，不将活动库草稿与另一个时点的快照混用。

尤其要复核：训练次数是否其实按天计算；RPE 是否混入未完成组；历史最大重量是否含热身；肌群关键词归类是否准确；空训练日是否有新格式快照覆盖。已有导出脚本不能替代这些检查。

### 步骤 3：训练与模板分析

按“执行 → 同动作表现 → 训练分布 → 模板对照”的顺序，先描述再解释。

| 指标 | 统一口径 |
|---|---|
| 训练次数 / 训练天数 | 次数按 `training_session` 记录数；天数按不同 `datestr`，两者分别列出 |
| 完成记录段 / 已完成正式组 | 当前 SQL 展开行数仅称完成记录段；正式组须按第 2.3.2 节恢复逻辑结构后计数，不能将一行直接称一组；两者均不自动等同于“有效增肌组” |
| 完成容量 | 经单位、负重角色和结构验证的独立完成非热身段，重量/次数均为有限正数时计算 `weight_kg × reps`，不重复计父级汇总；按第 2.3.3 节同时输出数值、状态与覆盖，状态判定包含无段结构的不适用记录 |
| 自重 / 计时 / 单侧动作 | 先按实际结构分别计段/逻辑组；没有可靠外部负重不计吨位，不能把容量缺失解释为训练量为零；不擅自乘以两侧 |
| RPE | 默认按独立完成非热身段统计合法独立评分，列样本数与可知的覆盖率；组级共享评分不复制、不与段级混合；RPE≥9 仅作记录特征 |
| 动作进步 | 优先比较同动作、同器械/单位、相近执行条件下的同重量次数或同次数重量；说明样本与日期 |
| 肌群分布 | 使用可复核的动作映射；关键词归类仅为启发式，未知保持未分类；不无说明地把复合动作全量重复分配给多个肌群 |
| 有氧 | 分运动类型、来源与单位统计；设备热量为估计，不与力量吨位混成一个训练量分数 |

禁止用跨动作的吨位大小直接判断刺激优劣，或仅凭单次最大重量认定力量退步/进步。若使用估算 1RM 等派生指标，须先明确公式、适用范围与误差，不能伪装为实测值。

模板对照另行检查：

- 优先用明确模板 ID / 元数据建立对应；仅凭标题相似的匹配标为候选，交用户确认。
- 确认模板的适用日期与版本；当前版本不能自动追溯为过去所有训练的标准。
- 原生 `movement`、组结构、递增规则须先解释清楚；名称、组数或规则不明时停止计算该项偏差。
- 区分“模板目标组”“实际记录段”“逻辑正式组”与“完整轮”；仅在目标结构、完成规则及排期层级一致时计算执行比例，部分完成单列。
- 模板存在不等于已经排期；不能凭模板数量或“四分化”名称自行推断训练频率、漏练或休息安排。

### 步骤 4：饮食与每日目标分析

1. 优先采用每日记录里的 `totals` 与该日 `foods.limits`，不拿今天的目标覆盖历史目标。
2. 分餐次、食物与日期查看已记录摄入；需要回算时，核对数量、单位和每 100g 营养，份量换算不明则不计算。
3. 每个营养素或热量指标分别计算，并保存目标有效性证据：
   - 差值 = 已记录摄入 − 当日目标；两者有效即可，包括已证实有效的零目标，单位为对应的 g 或 kcal。
   - 相对偏差 = 差值 ÷ 当日目标；仅当目标明确且大于 0 时计算。
4. 零若表示未设置或语义未知，按缺目标处理，差值和比率都不算；不能默认 API 中的0是有效目标。缺目标或没有适用的用户约定容差时，不计算达标率，不把小幅偏差任意划为“达标/不达标”。
5. 周均摄入只使用有记录的日期，并列“记录天数 / 区间天数”。未确认记录完整时，名称始终使用“已记录摄入”。
6. 目标改变时按生效日期分段，不能将不同目标下的数值直接混成一个执行率。
7. 每日热量以来源口径为准。蛋白质/碳水 4 kcal/g、脂肪 9 kcal/g 的换算仅作粗略核对；不因差异直接改写 API 热量或认定漏记。
8. 没有高/中/低碳日名称与映射时，只描述每日碳水目标的数值变化。`template_id` 相同不保证各日目标相同，也不能自行解释 ID 正负的意义。

**不得混同：摄入目标、已记录摄入、TDEE、训练设备估计消耗。** `limits` 可以用于目标执行核对，但不是 TDEE 测量值。

### 步骤 5：身体测量与结果指标

- 按类型、日期、单位列出真实测量；记录是否有统一的称重条件。
- 不把上次体重向后填满所有日期后当作实测，不跨长间隔插值制造连续趋势。
- 有足够测量时才展示周均/滚动均值，同时列真实测量次数和覆盖天数；不将仅含一个测量点的均值当作平滑趋势。
- 区间差值应写清两次实际测量日期；体重变化不能直接等同于脂肪或肌肉变化。
- 若体重样本稀疏或缺乏必要背景，先做描述性对照；不能精确反推 TDEE，也不能仅据此设定新的热量目标。体脂是否存在另按本次盘点判断。
- 以后若讨论 TDEE 估计，须先确认足够连续、条件一致的体重测量与较完整摄入记录，明确时间窗、假设和误差；体重变化不能简单按固定能量系数精确换算。

### 步骤 6：按日期联合核对

建立日级对照表，字段至少包括：日期、各域覆盖状态、训练类型、完成记录段/可知的逻辑正式组、容量数值与状态、有氧、已记录热量与宏量、当日目标及其有效性、差值/比率各自的配对资格、实际体重测量，以及已确认的背景信息。

连接原则：

- 使用来源中的 `datestr` / 日期作为日级键，明确日期边界；不要擅自按 UTC 时间戳重新分日。
- **先在各域按日期聚合，再连接**；直接连接训练组与食物明细会形成多对多乘积，重复计算摄入或训练量。
- 保留缺训练、缺饮食、缺身体测量的日期及状态，不用内连接将不完整日期静默丢弃，也不把空值补为 0。
- 比较前说明训练与饮食的重叠日期、可配对样本数、记录完整性及训练类型是否相近。
- 同日对照与跨日/跨周假设分开；恢复和训练表现不能默认仅由当天饮食决定。
- 按时间检查目标变化、模板版本、训练类型、测量条件等混杂因素。

可讨论的问题包括“某段时间目标偏差与可比训练表现是否同时发生变化”；不能直接写成“某种饮食导致了力量下降”。没有睡眠、疼痛、主观疲劳等信息时，应补问或保留未知，不能以 RPE 和容量代替全部恢复信息。

### 步骤 7：模型解释与复核

模型只接收与问题相关的事实底稿、指标定义、必要模板内容、已确认背景和缺失清单；不默认通读全部 Raw。

统一使用四类标签：

| 标签 | 含义 |
|---|---|
| 记录事实 | 数据中明确存在的日期、数值、目标、模板版本 |
| 计算结果 | 有查询、公式和单位可复现的汇总与差值 |
| 待验证假设 | 对原因或恢复的解释，必须带替代解释与不确定性 |
| 已确认决策 | 用户明确认可的调整、适用时间和复盘安排 |

每条主要结论使用“证据卡”：

```markdown
### 结论/问题编号：
- 类型：记录事实 / 计算结果 / 待验证假设 / 已确认决策
- 范围与样本：起止日期、覆盖情况、参与比较的次数/天数
- 证据：来源表、字段、Raw 路径或模板 ID/版本，及底稿中的对应项
- 算法：查询/脚本位置、筛选条件、公式、单位、分母
- 观察：只写能够由证据支持的描述
- 限制与替代解释：缺失、不可比项、记录习惯或其他混杂因素
- 可信程度：高 / 中 / 低，并说明依据，不编造概率
- 待用户确认：需要补充的背景或需要认可的判断
- 验证方式：下一次需要收集什么、用什么指标复查；阈值未约定时写“待约定”
```

“高可信”只描述该条证据能支持的范围，不自动意味着因果确定。主分析与复核应使用同一份冻结底稿和相同口径；第二模型可以检查遗漏和逻辑，但模型彼此同意不等于证据成立。模型和推理档位属于可替换的工具配置，记入本次运行信息，不作为流程准入条件或指标定义。

### 步骤 8：用户讨论、归档与下次验证

先向用户展示事实与候选解释，再问清：记录是否完整、模板是否确实在用、是否有临时调整，以及主观感受是否支持该解释。未获确认的判断保持“待讨论”。

归档遵循已有规则：

- `reports/weekly/YYYY-Www.md`：第一至五节、第七节遵循本地库→`scripts/export.py` 的正式事实链路；尚未接入并验收的新口径独立重算结果保留在核验底稿中。第六、八、九、十节中的判断经用户确认后再写。
- 不为饮食/身体联合分析擅自改变现有周报章节约定；正式分析时另约定补充附件路径，未确认时只在对话中展示补充底稿。
- `analysis/`、`notes/` 和 `plans/current.md` 中的个人判断、知识与调整只在用户确认后更新。
- 已有周报不得静默覆盖；`--write --force` 必须先检查并保留既有讨论内容，不能把强制参数当作覆盖许可。
- 本地 Markdown 计划调整与训记端写回是不同操作；远程写回仍需单独展示具体变更并等待确认。
- 下一次用相同定义复查用户已确认的问题；未收集到验证数据时写“尚不能验证”，不将旧假设累积成事实。

## 4. 冻结底稿与最小可复现产物包（格式约定，待工具实现）

计划使用 `data/normalized/analysis/<run_id>/` 保存本地分析产物；该目录处于现有 Git 忽略范围。`run_id` 使用 UTC 提取时间加唯一后缀，任务卡另记来源日期语义。**本轮未创建该目录或其中产物，也没有新增生成命令**。

```text
data/normalized/analysis/<run_id>/
  manifest.json       运行范围、准入、口径、来源与校验清单
  source.sqlite       一致性提取的派生库快照；供本次计算与复核只读使用
  metrics.json        机器可读事实与计算结果
  daily.csv           仅在需日级对照时生成；不需要时在 manifest 记 not_applicable
  exclusions.csv      按指标记录排除/不适用样本及原因
  facts/              必需时保存 Raw 派生的训练语义、段/组结构与完成依据
  inputs/             本次实际使用的指标定义、映射、结构规则与必要已确认背景内容
  queries/            本次实际执行的 SQL / Python 源码与参数定义
  review.md           初始只含事实摘要、证据索引和待讨论占位
```

### 4.1 `manifest.json` 必备信息

| 字段组 | 最少保存内容 |
|---|---|
| 运行身份 | `run_id`、UTC 提取时间、`workflow_version`、`metrics_version`、分析问题/模块、用户已确认目标的来源或 unknown |
| 窗口与基线 | 展示日期、表现比较样本/周期、联合观察时窗、选择理由、纳入/排除规则及方案修订记录 |
| 各域状态 | 所需日期与实际覆盖、同步/记录完整性分别为何、每个问题的准入状态/原因、API 采集时间或 unknown |
| 库与原始证据 | 数据库 schema、`source.sqlite` 校验和；选用 Raw 与请求元数据的本地路径、SHA-256、对应查询/分页或游标证据 |
| 计算实现 | Git commit（可得时）、实际参与计算的工作区文件校验和、查询参数、Python/SQLite 与相关依赖版本；不能只记 HEAD 而忽略未提交改动 |
| 映射及语义 | `inputs/` 中实际指标定义、动作/单位/负重/组结构规则与必要背景的文件名、版本和校验和；`facts/` 的派生证据关联；模板 ID/version/revision 与历史适用依据；未知项明确 unknown |
| 输出完整性 | 应生成/不适用的产物及原因、冻结事实文件的 SHA-256、独立重算与抽查结果、尚未解除的阻断项 |

注意：只有文件路径或数据库文件的哈希不足以重算，必须保留**可读取的一致性输入**。优先通过 SQLite backup API 等可靠方式提取一致快照，不能在写入期间直接复制主 `.db` 而漏掉 WAL。完成必要离线入库后再提取；此后本次查询、计算与复核均基于该快照。

Raw 保持只读，清单引用已选中的有效快照；同日旧/新快照不是额外训练或食物记录，不得重复累计。无法精确映射某个记录的 Raw 版本时标明来源粒度，不假装有逐条溯源。**库快照本身不包含已丢失的原始单位或组层级，不能单独声称足以复现这类指标**；还须冻结实际参与计算的派生事实和对应解释规则。无法恢复所需语义就降级/阻断，不靠库列名补齐。

`inputs/` 必须保存实际内容，而非仅版本字符串或哈希：至少包括本次选用的指标定义；需要时加入动作/单位/负重映射、组结构与完成传播规则、模板历史映射，以及最小必要的已确认用户背景（日期范围、确认来源、未知项）。不需要的文件在清单标 `not_applicable`，不制造空映射冒充已确认；不要无差别复制全部笔记或未获确认的个人判断。复现时不依赖仓库里已被更新的“最新版”定义或当前聊天上下文。

现有 `export.py` 尚无指定此分析快照的统一入口，不能宣称当前命令已经完成冻结。实施前，其输出仅作为辅助草稿；正式复现需保留在同一份快照上实际运行的独立查询，或先补齐导出工具的快照输入能力。

### 4.2 指标、日级表和排除清单

- `metrics.json` 每项至少含 `metric_id`、定义版本、窗口/分组、`value`、`unit`、`counting_unit`（涉及计数时）、`status`、`sample_n`、适用时的 `numerator`/`denominator`、缺失/不适用原因、查询 ID 和 `evidence_ids`。关键字段缺失不得以空字符串、零或“无问题”替代。
- `daily.csv` 先以完整日期轴建立行，再连接各域日级聚合；字段覆盖来源日期、同步/记录状态、训练次数/完成记录段/逻辑组、容量数值与状态、有氧、已记录摄入/当日目标及其有效性/偏差、当天真实测量及模板映射状态。CSV 空字段由对应状态列解释；0与 `null` 分开，禁止仅导出容量数值而丢失状态。
- `facts/` 中的实际段/逻辑组事实保存原始定位键、结构父子关系、运动类型、原始及转换单位、负重角色、完成/热身来源与派生依据；缺失要显式保留。若不能唯一连回某条标准化行，保留 Raw 定位的独立事实并说明关联限制，不以复用的 `set_index` 强行配对。
- 身体测量可以保留长表/独立事实记录，不因一天多类型测量而使日级表重复。无测量日期不得填成实测值。
- `exclusions.csv` 至少含指标 ID、稳定记录定位键、日期、主要原因与辅助原因。主要原因用于互斥计数，避免将同一条缺失样本反复相加。
- 排除规则包括：未完成、热身、不适用运动类型、自重未填外部负重、单位不明、字段缺失/异常、模板不可映射、窗口覆盖不足等；区分“本就不适用”与“数据质量不合格”。

### 4.3 冻结与复核规则

1. 来源快照、任务参数、`inputs/` 实际定义/映射/背景内容、`facts/` 派生事实、查询及指标文件通过校验后共同冻结；哈希清单不递归包含 manifest 自身，也不包含尚未形成的判断稿。
2. 主分析和复核读取同一个 `run_id`，不得只拿文字摘要复核而不查事实文件。发现数字分歧时按证据/查询定位，不以模型投票决定。
3. 复核阶段不能为了符合解释改写事实文件。补同步、修数据、改基线、改指标定义或发现计算错误时，建立新运行/修订 ID，并写明替代关系；旧包保留。
4. `review.md` 在用户确认前只保存事实、数据质量说明和判断占位。个人原因假设、恢复判断与建议先在对话中展示，用户确认记录后才写入相应复核稿；不以放在忽略目录为由绕过确认要求。
5. 后续复核稿采用追加修订文件（如 `review-r02.md`），不改写已冻结底稿。归档文件可记录其 `run_id`、证据编号和确认来源；不改变现有周报章节规则。
6. 本地产物仍是健康相关隐私数据：不含密钥、不默认提交 Git，不为模型解释发送整份数据库，只提供与问题相关的事实摘录。

## 5. 三类联合分析问题模板

每次只启用与任务相关的模板；这些模板约定比较方法，不预设存在关联或因果。

| 模板 | 输入与准入 | 比较对象 / 事先登记内容 | 标准输出 | 降级条件 |
|---|---|---|---|---|
| **J1 训练执行与目标摄入** | 日期覆盖、日训练聚合、同日摄入与目标；实际执行判断另需记录完整性 | 区分有训练记录、已同步无训练、覆盖未知；比较目标变化前后的日必须分段 | 带状态的日级对照、各营养素配对样本/差值、记录覆盖；不输出无依据的综合达标分 | 目标缺失只展示摄入；训练覆盖不明不把当天分类为休息；记录不全只称“已记录偏差” |
| **J2 可比训练表现与此前饮食** | 可比动作/训练样本、相应饮食覆盖、训练间隔和已知背景 | 在看结果前选同日或此前窗口，明确动作/器械/版本、表现指标、最低样本与排除条件；不默认固定天数 | 每次可比训练的表现、对应饮食窗口及覆盖、间隔/模板变更/睡眠或主观状态（存在时）；观察与替代解释分别列出 | 无可比样本或窗口不完整时只列时间线；背景未知限制解释，不从少量样本声称显著相关或因果 |
| **J3 体重变化与阶段执行** | 两次及以上实际测量、日期/单位与测量条件信息，区间内训练/摄入覆盖 | 以测量区间而非任意周界为主；趋势另需预设频率/间隔要求，不将极远历史点作当前阶段基线 | 实测点、明确区间差值、同期记录覆盖/目标变化/可比训练描述，列测量条件限制 | 稀疏仅描述点位；缺连续体重或较完整摄入不反推精确 TDEE，不把水分等波动当作脂肪变化 |

所有模板都必须显示未纳入配对的日期/样本数量及原因，不能只保留有利于某个解释的完整案例。用户补充的信息应标明是回忆、主观描述还是已有记录，不与库中实测混成同一种证据。

## 6. 假设、决策与验证闭环

证据卡用于单次复核；只有需要跨次验证的解释才建立假设记录，避免把每个数字变化都升级成假设。

假设最少字段：`hypothesis_id`、提出日期、问题/适用范围、来源 `run_id` / 证据 ID、当前解释、替代解释、预期观察、会削弱或否定它的结果、已知混杂因素、复查日期或所需可比训练次数、状态与状态变更依据。

| 状态 | 使用条件 |
|---|---|
| 待验证 | 已提出明确问题和验证方法，但尚无足够后续数据 |
| 证据支持 | 后续证据符合预设预测，仍保留范围、限制和替代解释；不等于证明因果 |
| 证据不足 | 到复查点仍缺样本、条件不可比或证据相互矛盾；不能当作已否定或默认成立 |
| 已否定 | 出现预先约定的反证或更可靠证据足以否定该假设在指定范围内的预测，注明依据 |
| 被替代 | 已由更明确的新假设替换，保留旧记录与新编号的关系；不静默删除历史 |

复查时先按原先登记的条件判读，再决定是否修订假设。改变窗口、阈值或预测应留新版本，不能在看完结果后重新定义“验证成功”。

**用户确认行动 ≠ 证实原因。** 用户同意调整训练量，只能形成一条已确认决策；不能因此把“此前表现变化由训练量导致”改成记录事实。决策另外记录确认日期/来源、生效范围、具体动作、观察指标、复查时点、停止或重新讨论条件，并关联而不混同假设编号。

个人假设和决策的首次落盘及状态更新仍遵循用户确认规则，可在正式分析后记录于用户认可的 `analysis/` / `notes/` 位置；本轮不新建个人假设日志，不替用户判定任何假设状态。

### 8.3 最小闭环与验收门槛

1. 按指标依赖推进：训练次数、天数和 `normalized_row` 完成记录段可先闭环，快照输入与指标入口也可先建设，不必等待全部 T7/T8。容量、外部最大重量及段级 RPE 启用前，须完成 T7 中各自所需的语义验证，并核实相关独立段、完成/热身、去重及评分层级；逻辑正式组与模板执行比例另须通过 T8 的对应结构验收及各自准入条件。容量或饮食目标指标启用前，分别通过 T9 / T10；P1 是实施排序，不是免验许可。工具未完成时仅允许保留完整依据的独立重算，缺失语义不得临时猜补；正式周报衔接遵循步骤 2 与步骤 8。
2. 选一个已结束且覆盖可核实的周，执行简版；只有问题需要时再检查并导入饮食。不要将附录的历史数量硬编码为当前验收预期。
3. 建立一致输入、任务卡、查询与冻结事实文件；检查数量、单位、分母和关键明细，再由另一轮独立重算或复核核对。
4. 需要联合分析时，仅加一个第 5 节模板，测试缺失日、不配对样本、目标变化、模板历史不明时能否正确降级。
5. 最后展示事实、限制与候选解释；用户确认后再记录判断/决策，并在下次按预登记条件复查。

通过标准：

- 不同 Agent 使用相同运行包和定义，得到一致事实（数值差异只能在预先登记的数值精度容差内，不能事后放宽）。
- 每个主要数字能追到查询、样本、单位和输入；没有把缺失、未入库或分页未完成当作零。
- 每个不具备条件的问题都有明确降级/停止原因，且不影响独立问题的输出。
- 对解释有分歧时能指出证据和替代解释，不以投票解决；给出进一步验证或反证所需的数据。
- 同步、离线入库、事实导出、个人判断归档及远程写回的权限边界没有混淆。

## 附录：流程复核与优化建议（2026-11-06）

> 本节记录对 v0.1 草案的复核建议，供下一版修订使用；列出的流程、产物与工具改动尚未实施，不替代正文及项目现行规则。

### 1. 总体评价

草案已清楚区分事实、计算、假设与决策，对缺失数据、历史模板适用性和跨域连接的边界也有明确约束。下一版应重点将这些原则转化为稳定、可重复执行的流程，补齐分析准入条件、统一计算口径、可复现产物和验证闭环。

保留以下主干设计：

- 缺失不等于零，摄入目标不等于 TDEE，当前模板不等于历史计划。
- 各域先按日期聚合再连接，避免明细多对多连接造成重复统计。
- 明确部分周、稀疏体重和记录不完整带来的限制。
- 将用户讨论、知识归档和下一次验证连接起来。

### 2. 按分析问题定义准入与降级条件

步骤 1 中“只交付数据质量清单”和“可以继续分析不受影响的部分”应统一为按问题判断，而不是整次分析通过或失败。

建议增加分析准入表：

| 分析问题 | 必要条件 | 条件不足时 |
|---|---|---|
| 训练次数、完成组 | 所选日期训练覆盖可核实 | 只报告已记录数量，不判断完整频率 |
| 同动作表现变化 | 动作、单位和执行条件可比 | 分别列记录，不给进退步判断 |
| 饮食目标偏差 | 当日已记录摄入及对应目标 | 缺目标则仅展示摄入 |
| 实际饮食执行情况 | 上述条件，加记录完整性确认 | 只称“已记录摄入偏差” |
| 历史计划执行率 | 当时适用版本、排期及实际训练映射 | 不计算执行率 |
| 饮食与训练联合解释 | 可配对日期、可比训练及必要背景 | 降级为时间线描述 |

同时区分两种完整性：

- **同步完整**：接口范围已获取、分页完成、数据已入库。
- **记录完整**：用户确实记录了实际训练或饮食。

同步完整不能证明记录完整。缺体重不应阻断训练分析，缺模板历史也不应阻断实际训练统计。

### 3. 将已确认的导出口径偏差列为工具修正项

复核时对照了 `scripts/export.py`，以下为当前实现与草案要求的差异。应优先在工具层统一，避免每次分析都由模型临时重算。

| 代码位置 | 当前实现 | 建议 |
|---|---|---|
| `render()` 中的 `strength_count` | “训练次数”按不同日期计数 | 分别输出训练次数和训练天数 |
| `movement_stats()` 的 RPE 收集 | 已排除热身，但未限定已完成组 | 按完成且非热身组统计，并输出覆盖率 |
| `prior_max_weight()` | 历史最大重量未排除热身 | 历史与本期使用一致筛选 |
| `day_status()` | 无训练行时，仅凭旧路径文件存在判断休息 | 检查有效响应内容及最新覆盖证据 |
| `render()` 的前四周比较表 | 没有各周覆盖状态 | 增加覆盖天数、是否完整及比较资格 |

以上为本次复核时的代码状态；实施修正后应更新本清单，不将其长期保留为现存问题。

### 4. 固定指标定义和比较基线

建议建立统一指标字典，每个指标至少定义：

> 指标 ID、来源字段、筛选条件、单位、分母、缺失处理、适用范围、口径版本。

优先固定：

- 完成正式组数及容量可计算组的覆盖率。
- RPE 样本数、覆盖率和汇总方式。
- 饮食记录日均值、含目标日的配对偏差。
- 同动作表现的比较单位。
- 模板执行比例的分子、分母。

周报窗口与表现评价窗口应分开：

- 周报按 ISO 周组织。
- 动作表现按可比训练次数或已确认训练周期观察。
- 体重按实际测量覆盖选择窗口。

例如，分化训练跨周错位可能改变单周肌群组数，不能直接解释为漏练或刺激下降。比较基线应在查看比较结果前选定并记录理由；需要调整时保留变更原因，避免事后挑选最支持某种解释的日期。

### 5. 明确冻结底稿的实现与复现信息

正文要求主分析与复核使用同一份冻结底稿，但尚未定义其形式。建议在流程定稿时约定产物路径，并定义最小分析产物包：

```text
manifest.json       分析范围、提取时间、各域截止时间、口径版本、来源快照
metrics.json        机器可读的事实与计算结果
daily.csv           日级对照表
review.md           主要发现、待讨论问题、证据编号
```

其中涉及个人判断的文件，仍按项目规则经用户确认后写入。复现信息还应包含：

- 查询或脚本版本。
- 参与分析的来源快照及必要校验信息。
- 模板 revision。
- 动作映射版本。
- 各指标排除的样本数量及原因。

只记录“来源是 `data/training.db`”不足以复现：数据库后续更新后，同一个查询可能得到不同结果。

### 6. 为联合分析增加可执行的问题模板

当前联合部分明确了如何连接，但连接后如何分析仍较开放。建议先提供三种常用模板，每种均规定输入、比较对象、输出和降级条件。

**训练执行与目标摄入：**

- 区分训练日、已确认休息日和覆盖未知日。
- 展示对应日期的摄入、目标与偏差。
- 记录完整性不足时，保留“已记录”限定。

**可比训练表现与此前饮食：**

- 先建立可比训练样本。
- 事先明确观察同日还是此前某个时间窗，并说明依据。
- 同时列出模板变化、训练间隔、睡眠和主观状态等已知背景。

**体重变化与阶段执行：**

- 使用真实测量日期。
- 检查测量区间内的饮食记录覆盖。
- 先描述共同变化，再讨论解释。

这些模板用于减少临时选择分析方法的随意性，不预设饮食与训练表现存在因果关系。

### 7. 补充假设的验证、否定与状态管理

建议在证据卡基础上，为需要跨次跟踪的假设增加：

- 假设编号及提出日期。
- 预期观察到什么。
- 什么结果会削弱或否定它。
- 复查时间或所需可比训练次数。
- 状态：待验证／证据支持／证据不足／已否定／被替代。

需明确：**用户确认可以使建议成为决策，但不会自动使原因解释成为事实。** 例如，用户同意调整训练量，只表示接受该行动，不能因此认定此前表现变化就是训练量导致的。

1. 将“当前数据盘点”和“下一轮具体动作”移到带日期的附录，避免“饮食表为零”“先导入 27 天记录”等一次性状态长期混入执行规则。
2. 提供简版与专题版流程：常规周报只展开相关域，涉及饮食、身体或模板问题时再执行对应模块。
3. 将 `high` / `xhigh` 等模型配置移到工具使用说明；主流程保留复核要求，保持对不同 Agent 的适用性。

### 9. 建议实施顺序与验收目标

1. 修正事实导出的口径差异。
2. 补齐分析准入表、指标字典和底稿格式。
3. 选择一个覆盖可核实的完整周，试跑最小闭环。
4. 再完善联合问题模板和跨周假设跟踪。

验收目标：**不同 Agent 使用同一份数据和同一套定义，应得到一致的事实；对解释存在分歧时，应能指出分歧依据，以及下一步需要什么证据验证。**
